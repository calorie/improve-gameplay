# コアの改善を反復する

ゲーム全体の改善、新規ゲーム、または依頼範囲内で体験構造を見直す時に使う。通常の局所変更はSKILL.mdの短い手順で扱う。

## 開始と再開

1. 既存仕様・実装・進行・評価履歴を読み、対象版、操作・録画・音の確認手段、作業範囲、予算を把握する。別のアクティブなセッションやその作業領域を操作しない。未許可のインストール・購入・公開・全体設定の変更はしない。
2. **作品ごとの契約**に対象プレイヤー、狙う魅力、守る表現品質、意図した謎、今回の評価範囲を短く記す。個人の画風・エンジン・ジャンルを汎用規則にしない。未定事項は仮説として明示し、小試作で調べる。仕様書を巨大化させない。
3. 既存の予算を使う。品質改善の自律反復に予算が未指定なら、運用初期値は最大30分・3実験、同じ原因仮説で2回改善なしなら見直す。制作手法の標準値や、通常の依頼を途中で切り上げる期限ではない。所要時間は見積り、実績は実測し、取得できないトークン数を捏造しない。

## 反復する

品質改善では [評価と試遊](evaluation.md) を読み、以下を実行する。

1. **観察**：瞬間・一連のプレイ・対象全体で、最も魅力的な点、退屈な点、成立を妨げる点を実行証拠へ結ぶ。作者の設定と、ゲームで提示された情報と、プレイヤーが理解した事実を分ける。
2. **選択**：最重要の未解決問題から原因仮説を一つ選ぶ。作業を「問題→原因→変更→機能確認→面白さ確認→全体への悪影響確認」で定義する。操作・物語・UI・表現をまたぐ変更も、一つの体験のためならまとめる。
3. **作業前点検**：[記録形式](record-format.md) に従ってプロジェクト側へ記録し、下記チェッカーを通す。非ゼロなら作業選択または記録を直す。問題IDを付けるだけで無関係な変更を正当化しない。
4. **実装・比較**：許可済みの作業を自律的に進める。実際の入力経路で動かし、前後の場面も含めて修正前後を比較する。紙・映像・コードのみの試作は証明できる範囲を限定する。
5. **三つを別々に判断**：機能したか／理解できたか／楽しくなったか。人間試遊では理解の質問だけで終えず、楽しい・退屈な瞬間と、続きを経験したいか、その理由を確認する。比較できる場合は修正前後の好みも聞く。AIの予測は明示して更新し、人間不在でも独立した改善を続ける。
6. **採否と継続**：改善と悪化を記録し、採用・暫定採用・撤回・別案を選ぶ。同じ手段の数値調整で停滞したら原因仮説や体験構造へ戻る。仮説の名前だけ変えない。予算内は次の重要問題へ進む。終了時は安全に状態を保存し、未達と次の確認を残す。

```bash
python3 <skill-dir>/scripts/check_cycle.py <iteration.json> --previous <previous-iteration.json>
```

初回だけ `--previous` を省く。記録は [説明用サンプル](../assets/iteration.example.json) を構造の参考にし、架空の観測を実証として転用しない。Pythonがなければ同じ規則を手で確認し、「機械検証なし」と記録する。

## 作業を選ぶ規則

| 状況 | 次の作業 |
|---|---|
| 核の魅力が未成立 | 遊び・構成・反応の試作、または仮説を分ける証拠収集 |
| 芝居・音・UIが理解や感情を壊す | コアへの修正として扱う。見た目という理由で後回しにしない |
| 必要な表現を今の道具で作れない | 小さな技術試作、制作工程・学習・適合素材を比較。品質基準を下げて合格にしない |
| 新規ゲーム | 全体の体験を見通し、小さなコア試作→表現も含む代表区間→展開。各段階で全体へ戻る |
| 局所的な変更 | 影響範囲と前後を確認。重要変更と展開・完成の節目で全体を確認 |
| 人間試遊や音などの証拠がない | 該当判定を未検証にし、可能な改善を続ける。初見者を演じて証拠にしない |

## 短い報告と引き継ぎ

「今回狙った魅力／変更／観測／面白さの予測と人間の証拠／損失・未達／遊んで確認する箇所／次の一手」を短く返す。最新の版、契約、証拠、未解決問題、失敗した案、予算実績をプロジェクトに残し、別セッションでもそこから再開する。

チェッカーは記録・証拠の版と範囲・優先順位・予算を点検する補助である。面白さの採点、資料の真偽の認証、無断操作の阻止、エンジン接続は行わない。意味の評価と実行は利用中のAIと利用可能な道具が担う。
